# Using the WCA@IBM API

## Capabilities

1. Send an open-ended chat message to WCA.
2. Send a chat message plus history as context.
3. Use all of WCA's chat commands.
4. Provide code references for additional context. 

## Access: How to, Scope, Limits

1. Create a new issue in this repository using the _API key access_ template: https://github.ibm.com/code-assistant/wca-api/issues/new?assignees=&labels=&projects=&template=api-key-access-to-wca.md&title=API+key+access+to+WCA
2. The "contact person" identified in the request will get an _API Key_ to access the API
   1. Do _not_ share this API key with other teams.
   2. Do _not_ put this API key into GitHub, or any documentation that is visible outside your team.
3. Access to the API is free of charge for your WCA@IBM use cases.
   1. We'd _love_ to hear from you what you're building!
   2. You can _not_ use this API key for use within an IBM product, or when working with customers. If you want to use the API for external-facing work, let us know, and we'll figure something out.
4. The API usage is rate-limited to 40 requests per second. This rate limit is shared between _all_ teams using the API. So, please be nice to your fellow teams. If you have a use case that will require a high rate limit, talk to us.

### WCA API Request

The WCA API request contains the following key parts:

- Authentication header
- Request-ID header
- Chat message (JSON payload)
- Referenced files

#### Authentication

- Each call needs to contain a bearer token, created from your API Key. The token is passed in the HTTP header of the API request :

  ``` --header 'Authorization: Bearer <access_token>' ```
  
- You create the bearer token by calling IBM Cloud IAM :  https://cloud.ibm.com/apidocs/watson-data-api#creating-an-iam-bearer-token
- Each bearer token is valid for 60 minutes. You _must_ cache the bearer token instead of re-generating it for every request. Otherwise, the IAM service will punitively rate limit you.

#### Request payload encoding

The WCA API is protected by a CIS firewall. To avoid that your payload gets rejected (which can happen especially when you send code), encode your payload as base64. See our examples for details.

#### Request-ID 

All WCA API requests should contain a unique request id to identify the request uniquely in the WCA backend. The expected format of the request id is a UUID. It is to be included as part of the HTTP header for the API request.

``` --header 'Request-ID: <request-id>' ```

If a request id is not sent as part of the request, WCA will generate one. However, note that it is strongly recommended that API users include a request id in the header. This helps in providing better support for issues related to APIs. 

#### Chat Messages

A chat message is the JSON structure that is used to communicate with WCA. The chat request and response payloads both contain one or more messages.
A message contains two parts :

- The ```content``` part is an instruction in the case of a request payload. In the response payload the content contains the response that is generated by WCA.
- The ```role``` part which takes one of ```USER``` or ```ASSISTANT```. An instruction from the user has the ```USER``` role and a response from WCA contains an ```ASSISTANT``` role.

#### Using "chat history"

- The WCA API expects a sequence of `messages` in chronological order.
- Note that there is no timestamp in the message. The messages are expected to follow a sequence starting from the oldest and ending with the newest. This sequence needs to be maintained by the API client.
- Example payload:

  ```json
  "messages": [
    {
      "content": "Write quicksort in Java",
      "role": "USER"
     },
     {
       "content": "\n```java\n// Assisted by WCA@IBM\npublic class QuickSort ...```",
       "role": "ASSISTANT"
     },
     {
       "content": "rename the class to QuickSortExample",
       "role": "USER"
     }
   ]
   ```

- The WCA API does _not_ keep any conversation history. Your application needs to store history as appropriate, and provide it through the API.
- Ensure that the roles are always alternating: user-assistant-user-assistant-user
- The _last_ message in the sequence has to be the _latest_ instruction from the user.
- As a best practice do not include responses which contain the "use_for_context" set to false. These are typically system messages which indicate either HAP/NPR detection or the code being blocked due to Similarity match

Refer to the section on Context Sizing in this document for details on maximum history size that will be accepted by WCA.

#### Providing file references

To provide content from a local file to WCA:

1. Reference the file as part of your chat message by specifying the name of the file along with its extension. This ensures that WCA creates the right prompt in the backend. The format of the reference is: `[<file name>](file-<file path>)`. Sample instruction:

   ```
   Rename the variables in [customer.py](file-/usr/local/alex/customer.py)
   ```

2. Add the file contents as part of a `files` array to your API call. See our examples in [REST API](https://github.ibm.com/code-assistant/wca-api/tree/sample_curls/rest_api/Readme.md)(e.g., for the `/translate` command) or the [WCA CLI ](https://github.ibm.com/code-assistant/wca-api/tree/sample_curls/WCA_CLI/Readme.md). The CLI contains the `call_wca_api` in `wca_cli.py` that shows how to construct this payload in Python.
3. Note: You can also reference specific _classes_ or _methods_ in the instruction just by specifying their names in the instruction. Example:

   ```
   /document [check_eligibility](file-/usr/local/alex/customer.py)
   ```

Refer to the following section for details on the maximum size of files that will be processed.

#### Context Sizing for all non-Java related instructions

- Input prompt including context from referenced files and history can take up to 28k tokens
- When both history and file content are provided as context, a maximum of 3k and 25k tokens are accepted for history and file contents, respectively.
- Any excess tokens are truncated. History is truncated starting from the oldest message. File contents are truncated starting at the bottom of the file.
- If file contents take less than 25k tokens, the remaining quota is used for history.
- WCA currently supports generating a maximum of 4k tokens.

#### Context Sizing for all Java related instructions

- Input prompt including context from referenced files and history can take up to 4k tokens
- When both history and file content are provided as context, a maximum of 1k and 3k tokens are accepted for history and file contents respectively.
- Any excess tokens are truncated. History is truncated starting from the oldest message. File contents are truncated starting at the bottom of the file.
- If file contents take less than 3k tokens, the remaining quota is used for history.
- WCA currently supports generating a maximum of 4k tokens.

### WCA API Response

The key elements of the WCA API response are :

- the chat message response
- similarity matches
- error details

#### The chat message response

The message part of the response contains `content` and `role` which are the same as explained in the Chat Messages section of this document.
The response message also contains the following fields:

- ```type``` : this indicates the use case type. This may be one of CHAT, DOCUMENTATION, TEST_GENERATION, EXPLANATION, CODE_TRANSLATE, IBM_DOCS.
- ```context``` : this contains the context that was used for generating this response. This is typically all the chat history and referenced file content in the request, except in the case of the ```docs``` command in which case this field shows the context that was fetched from the backend to answer the question about an IBM product. This field can be used to check if the correct context was used to generate the response.
- ```use_for_context```: this is a boolean that indicates if this response should be used as context for subsequent messages. This is false when the response is a system message that indicates an HAP/NPR/Similarity match was detected. In all other cases it is true. Use this field to decide if this response should be included in the chat history for subsequent message.

#### Similarity matches

WCA performs a similarity match for all code generation use cases (CHAT/TEST_GENERATION/TRANSLATE), to check if the generated response matches with data that was used for training the large language model (LLM). If a match is found, the similarity matches part of the response contains the details of the match such as the URI of the code and the license type. This data will be populated only if the degree of match has crossed a certain permissable threshold resulting in the response being blocked.
Refer to the [Rest_API example ](https://github.ibm.com/code-assistant/wca-api/blob/main/rest_api/Readme.md#expected-response-7) to see how this looks.

#### Error Details

If there is an error in processing the request, the details are populated in the ```error``` field in the response. 
Example error message when a non-technical instruction is sent out to WCA:

```
"error": {
        "code": "WCA-0102-W",
        "message": "The request might not be about coding. Enter a code-related question for a better response."
    }
```

Similarity matches resulting in code being blocked and HAP (Hate,Abuse, Profanity) detection are other instances when you will see data in the error field.
